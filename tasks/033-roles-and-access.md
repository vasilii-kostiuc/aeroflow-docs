# Роли и права доступа: администратор и диспетчер

Status: Done
Bounded context: User Access (Core — роли, пользователи, контроль доступа),
presentation (aeroflow-web — навигация и маршруты по ролям, экран пользователей)
Service: aeroflow-core, aeroflow-web
Change type: Domain, Application, API, Security, Frontend

## Goal

Закрыть дыру: сейчас `POST /api/v1/register` открыт всем, а для всего
`/api/v1` проверяется только аутентификация. Любой, кто достучится до core,
может зарегистрироваться и запустить экстренное объявление, снять экстренный
режим или удалить папки. README описывает две роли — администратор и
диспетчер — с разными правами; этот срез их вводит.

## Decisions

### Роли

* роль пользователя — одна из: `ROLE_ADMIN` (администратор), `ROLE_DISPATCHER`
  (диспетчер) или **нет роли** (учётка есть, доступа к API нет — например,
  сотрудник уволен или ещё не допущен). Enum `UserRole` в `UserAccess\Domain`;
* иерархия: администратор может всё, что диспетчер (`role_hierarchy`:
  `ROLE_ADMIN: [ROLE_DISPATCHER]`);
* роли читаются из БД на каждый запрос (провайдер грузит пользователя по email из
  JWT), поэтому смена роли действует сразу, без перевыпуска токена;
* `User::changeRole(?UserRole)` идемпотентна, событие `UserRoleChanged` — только
  при фактической смене;
* **инвариант «в системе всегда есть администратор»**: нельзя снять роль
  администратора с последнего администратора (`409`). Проверка в application
  handler через подсчёт администраторов в репозитории;
* `User::changePassword(hash)` — администратор задаёт пароль (почтового
  восстановления нет); событие `UserPasswordChanged`. Выданные пользователю
  refresh-токены при этом отзываются: старая сессия не должна переживать смену
  пароля.

### Кто что может

| Что | Диспетчер | Администратор |
|---|---|---|
| `/dispatcher/*` — доска, очередь, стоп, дополнительные и экстренные объявления, снятие режима | ✓ | ✓ |
| действия над рейсом: `POST /flight-occurrences:ensure-manual`, `:start-next-manual`, `/{id}/check-in:open`, `check-in:close`, `boarding`, `arrival` | ✓ | ✓ |
| отмена ожидающего объявления `POST /announcements/{id}/cancel` | ✓ | ✓ |
| чтение справочников для панели (`GET`): рейсы, аэропорты, occurrences, объявления, выходы, стойки, языки конфигурации | ✓ | ✓ |
| всё остальное: справочники на запись, конфигурации объявлений, пресеты, аудиобиблиотека, пользователи, строгое создание occurrence | — | ✓ |
| `GET /me` | ✓ | ✓ (и пользователь без роли) |

Правила — в `access_control` `security.yaml`, одним местом: сначала публичные,
потом диспетчерские, потом «всё остальное под `/api/v1` — администратор». Так
новый эндпоинт по умолчанию закрыт до администратора, а не открыт всем.
Пользователь без роли получает `403` на всё, кроме `GET /me`.

### Пользователи

* публичная регистрация **убирается**: `POST /api/v1/register` удалён;
* администратор управляет пользователями: `GET /api/v1/admin/users`,
  `POST /api/v1/admin/users { email, password, role }`,
  `PATCH /api/v1/admin/users/{id} { role }` (`role: null` — без доступа),
  `POST /api/v1/admin/users/{id}/password { password }`;
* `GET /api/v1/me` — текущий пользователь с ролью; web обновляет по нему роль в
  сессии при загрузке приложения;
* первый администратор — консольной командой
  `app:users:create <email> --role=admin` (пароль спрашивается интерактивно или
  передаётся `--password`); той же командой можно создать любого пользователя;
* миграция: всем существующим пользователям выдаётся `ROLE_ADMIN` — до этой
  задачи у всех и так был полный доступ, поэтому никто не теряет доступ и
  система не остаётся без администратора; лишние права администратор затем
  снимает. Dev-фикстуры: `admin@` — администратор, `dispatcher@` — диспетчер,
  `operator@` — без роли (показывает экран «Нет доступа»).

### Web

* роль берётся из сессии (`user.roles`) и обновляется по `GET /me` при старте;
  скрытые кнопки и пункты — только удобство, решение принимает backend;
* навигация по ролям: диспетчер видит «Панель диспетчера»; администратор —
  всё, включая новый экран «Пользователи»;
* маршруты защищены по ролям (`RequireRole`); недоступный маршрут показывает
  страницу «Нет доступа» (архитектура web предусматривает `access denied`);
* после входа — стартовая страница по роли: диспетчер на `/dispatcher`,
  администратор на справочники, без роли — «Нет доступа»;
* экран «Пользователи» (`/users`, feature `users`): таблица (email, роль),
  «Новый пользователь» (email, пароль, роль), смена роли, «Задать пароль».
  Серверные `409/422` — в формах.

## Out of Scope

* удаление и блокировка пользователей отдельным флагом (роль «нет» закрывает
  доступ);
* восстановление пароля по почте; смена пароля самим пользователем;
* авторизация между сервисами (`/internal/v1` остаётся на сетевом доверии);
* журнал действий (аудит) — отдельная задача; события `UserRoleChanged` и
  `UserPasswordChanged` для него уже публикуются.

## Acceptance Criteria

* `POST /api/v1/register` больше нет;
* без роли — `403` на все `/api/v1`, кроме `GET /me` и публичных эндпоинтов;
* диспетчер может всё из таблицы выше и получает `403` на администраторские
  эндпоинты (например, `POST /admin/audio-folders`, `GET /admin/users`);
* администратор может всё;
* снять роль с последнего администратора нельзя (`409`);
* смена пароля отзывает refresh-токены пользователя;
* существующие пользователи после миграции — администраторы;
* web: диспетчер не видит справочников и не может открыть их по ссылке («Нет
  доступа»), администратор видит «Пользователи» и управляет ролями.
