# Transactional outbox для интеграционных сообщений core

Status: Done
Bounded context: Announcements (издатель команд в playback); инфраструктура
доставки core
Service: aeroflow-core
Change type: Integration, Infrastructure

## Goal

Закрыть компромисс первой версии в core: команды в playback публиковались в
RabbitMQ **после** коммита, из памяти процесса, и в окне между коммитом и
отправкой терялись молча.

* **Брокер недоступен в момент действия диспетчера.** Переход `FlightOccurrence`
  и `Announcement` уже закоммичены, отправка падает — диспетчер получает 500,
  повторный клик даёт 409. Задание в playback не появится, вместе с ним теряются
  остальные события той же транзакции.
* **Процесс умер между коммитом и отправкой** — то же без 500.
* **Нет publisher confirms** — успешный `dispatch` не гарантировал, что брокер
  принял сообщение.

Команда в playback должна уходить тогда и только тогда, когда закоммичено
изменение состояния, которое её породило.

## Decisions

* **В outbox — интеграционные сообщения**, а не доменные события: доменные события
  остаются внутренними для контекста и не становятся долговечным форматом в БД.
* **Запись — через существующие порты, обработчики не меняются.** Реализации
  портов заменены алиасом в `services.yaml`: `OutboxPlaybackRequestPublisher`
  (request, cancel, stop, stop_repeat → очередь `announcement_playback`),
  `OutboxEmergencyModePublisher` (activate, deactivate → `emergency_commands`).
  Адаптер кодирует сообщение тем же сериализатором, что и транспорт Messenger, —
  формат на проводе не меняется, playback не трогается.
* **Запись — в той же транзакции.** Таблица пишется через DBAL-соединение ORM.
  Порядок middleware `command.bus` — `doctrine_transaction` →
  `DomainEventTransactionMiddleware`: доменные события по-прежнему буферизуются на
  время use case и отдаются обработчикам после него, но до коммита. Ошибка
  обработчика события откатывает весь use case. Правило: обработчики доменных
  событий не обращаются к внешним системам — всё, что уходит из сервиса, идёт через
  outbox.
* **Таблица `outbox_message`** (своя, не `messenger_messages`): `id` (порядок),
  `destination` (имя очереди), `body` (JSON контракта), `headers`, `created_at`.
  Отправленная строка удаляется. Таблица не маппится в ORM — schema diff её
  игнорирует (`schema_filter`).
* **Relay** — `app:outbox:relay`, один процесс, контейнер
  `aeroflow_core_outbox_relay`:
  * опрос таблицы раз в 200 мс, после ошибки — пауза 1 с;
  * строго по порядку `id` внутри очереди: если отправка не удалась, остальные
    сообщения этой очереди ждут следующего прохода, другие очереди продолжают;
  * `emergency_commands` идёт первой — смысл отдельного транспорта (ADR 002,
    уровень 2) сохраняется;
  * отправка через `Connection` AMQP-транспорта Symfony по тем же DSN (та же
    топология exchange/queue) с `confirm_timeout`; строка удаляется только после
    подтверждения брокера. Доставка at-least-once, дубль отбрасывается playback по
    `messageId`.

## Out of Scope

* outbox в playback (события в core и команды агенту) — playback остаётся на
  post-commit publisher;
* наблюдение за outbox на экране «Состояние системы» и heartbeat relay;
* `LISTEN/NOTIFY` вместо опроса, защита от второго экземпляра relay.

## Acceptance Criteria

* действие диспетчера не обращается к брокеру: при остановленном relay (или
  брокере) запуск объявления успешен, сообщение ждёт в outbox и уходит после
  восстановления;
* запись в outbox откатывается вместе с транзакцией use case;
* relay доставляет по порядку внутри очереди, `emergency_commands` — первой;
  неудачная отправка не пропускается и не задерживает другие очереди;
* формат сообщений на проводе не изменился;
* обработчики `Publish*` не изменены.

## Verification

```bash
# aeroflow-core
php bin/phpunit
```

Ручная проверка: `docker stop aeroflow_core_outbox_relay` → запустить объявление в
панели диспетчера (успешно, строка в `outbox_message`) →
`docker start aeroflow_core_outbox_relay` → объявление в очереди и звучит.
