# Состояние системы: панель администратора и предупреждения диспетчеру

Status: Done
Bounded context: новый служебный модуль `SystemStatus` в aeroflow-core (не
доменный контекст — наблюдение за инфраструктурой); aeroflow-playback публикует
heartbeat; aeroflow-web — экран и баннер
Service: aeroflow-core, aeroflow-playback, aeroflow-web
Change type: Integration, Infrastructure, API, Frontend

## Goal

В системе оповещения самый опасный сбой — тихий: агент упал или воркер
playback не работает, диспетчер нажимает «Начало регистрации», объявление
встаёт в очередь, а в зале тишина. Сейчас это видно только по заданию, которое
вечно «играет». Нужно, чтобы:

* администратор видел состояние всех компонентов на одном экране;
* диспетчер видел в своей панели предупреждение, если объявления сейчас не
  прозвучат.

Это встроенная панель для on-prem установки без отдельной ops-команды, а не
замена полноценному мониторингу (Prometheus/Alertmanager — возможное будущее
решение, см. Out of Scope).

## Почему heartbeat, а не число потребителей очереди

Транспорт AMQP в Symfony Messenger опрашивает очередь (`basic.get`), а не держит
подписку: у очередей, которые разбирают воркеры core и playback, в RabbitMQ
всегда 0 потребителей, даже когда воркер жив. Число потребителей честно
показывает только агента (.NET держит подписку `basic.consume` на
`agent_commands`). Поэтому живость воркеров Symfony — по heartbeat.

## Decisions

### Heartbeat воркеров

* каждый воркер Messenger (слушатель `WorkerRunningEvent`) не чаще раза в
  15 секунд сообщает, что жив, и перечисляет транспорты, которые он разбирает;
* **playback** публикует факт `playback.heartbeat` в уже существующую очередь
  `playback_events` — тем же способом, что факты экстренного режима (задача
  026): контракт `event`, `messageId`, `occurredAt`, `schemaVersion: 1`, плюс
  `transports` (список), `pendingJobs` (число ожидающих заданий) и
  `playingSince` (с какого момента играет текущее задание, или `null`). Отправка
  heartbeat не должна ронять воркер: ошибка брокера только логируется;
* **core** принимает `playback.heartbeat` и хранит последнюю отметку на каждый
  набор транспортов (таблица `system_heartbeat`, строка на воркер); свой воркер
  core пишет heartbeat в ту же таблицу напрямую;
* heartbeat свежий, если ему не больше 60 секунд. Транспорт «обслуживается»,
  если его перечисляет хотя бы один свежий heartbeat.

### Что проверяет core

| Компонент | Как |
|---|---|
| База данных core | ответ на запрос |
| RabbitMQ | management API (`RABBITMQ_MANAGEMENT_URL`) |
| Аудиоагент | число потребителей на `agent_commands` ≥ 1 |
| playback: команды воспроизведения, экстренные команды, события агента, повторы по расписанию | свежий heartbeat для `announcement_playback`, `emergency_commands`, `agent_events`, `scheduler` |
| core: приём событий playback | свежий heartbeat core-воркера для `playback_events` |
| Синтез речи | `GET {TTS_BASE_URL}/health` |
| Очереди | `messages_ready` каждой очереди; больше 20 — предупреждение |
| Воспроизведение | `playingSince` из heartbeat playback: дольше 10 минут — предупреждение «возможно, агент завис» |

Статус компонента: `ok`, `warning`, `down` или `unknown` (проверка невозможна —
например, RabbitMQ недоступен, поэтому про агента ничего не известно).

### API

* `GET /api/v1/admin/system-status` (администратор) — все компоненты: ключ,
  название, статус, пояснение; плюс время проверки;
* `GET /api/v1/dispatcher/system-alerts` (диспетчер) — только то, из-за чего
  объявления сейчас могут не прозвучать или экран очереди отстаёт, понятным
  языком, без внутренних имён очередей. Пустой список — всё в порядке.

### Web

* экран «Состояние системы» (`/system-status`, администрирование): список
  компонентов со статусом и пояснением, общий итог сверху, обновление раз в
  10 секунд;
* в панели диспетчера — баннер с предупреждениями из `system-alerts`
  (обновление раз в 15 секунд); при ошибке самого запроса — «Состояние системы
  неизвестно».

## Out of Scope

* heartbeat самого агента с подробностями (режим `Simulate`, наличие `ffplay`,
  версия) — следующий срез; сейчас агент виден только как «подключён / нет»;
* история состояний, графики и тревоги по почте или в мессенджер —
  Prometheus/Alertmanager/Grafana, отдельное решение;
* восстановление зависшего задания — отдельная задача; здесь только видно, что
  оно зависло.

## Acceptance Criteria

* playback публикует `playback.heartbeat` не чаще раза в 15 с на воркер, ошибка
  отправки не останавливает воркер;
* core хранит последний heartbeat каждого воркера и свой собственный;
* `GET /admin/system-status` показывает перечисленные компоненты; остановленный
  воркер становится `down` через минуту, отключённый агент — сразу;
* `GET /dispatcher/system-alerts` пуст при исправной системе и объясняет
  проблему, когда агент или playback недоступны;
* экран «Состояние системы» доступен только администратору, баннер виден
  диспетчеру.

```bash
# aeroflow-core, aeroflow-playback
php bin/phpunit

# aeroflow-web
npm run lint && npm run typecheck && npm run test:run && npm run build
```

и в панели диспетчера предупреждение; запустить обратно — пропадает.
